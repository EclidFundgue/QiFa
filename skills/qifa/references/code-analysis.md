# 代码库分析（source-analysis 后半）

目标：把仓库变成可讲解、可引用、可核查的结构化来源。**只读仓库；不修改、不安装、不运行有副作用的命令。**

## 获取

| 输入 | 处理 |
| --- | --- |
| 本地路径 | 直接读；`git -C <path> rev-parse --show-toplevel` 确认仓库根；不改任何文件 |
| git URL | 浅克隆到 `source/code/`（`git clone --depth 1`）；只读 |

记录到 `source-model.sources[]` 的 `origin`：本地路径或 URL 原文（不记录 commit hash）。

## 抽取顺序

1. **产品目标**：README/文档里的"这个项目解决什么问题"。
2. **技术栈与运行方式**：语言、构建/启动命令、配置文件。
3. **目录与模块地图**：`files[]`（只记讲解需要的），每个模块一句话职责。
4. **入口**：CLI/服务/库的入口文件与函数（`entrypoints[]`）。
5. **调用链**：3–5 条最重要的主流程，从入口到落点（`dataflow[]` 的 `from`/`to` 用 `path:符号`）。
6. **关键符号**：讲解会用到的类/函数/常量（`symbols[]`）。
7. **与论文的映射**（混合输入时）：论文方法 ↔ 代码实现的对应表。

## 引用格式

- 一律 `path:符号`，如 `src/server/app.py:create_app`、`pkg/parser/lexer.ts:tokenize`。
- 不写行号（易漂移），不写 commit hash；文件名用仓库相对路径。
- 引用必须指向真实存在的文件与符号（校验器会检查本地文件是否存在）。

## 讲法（进入 chapter-design 前想清楚）

好的代码课按"问题 → 结构 → 路径 → 细节"递进，而非按目录念：

1. **问题**：这个仓库存在的理由（用户价值）。
2. **结构**：模块地图 + 职责边界。
3. **路径**：跟着一次真实调用走（输入从哪来、在哪变形、从哪出去）。
4. **细节**：只挑承担关键逻辑的 3–5 个符号，讲清设计取舍。
5. **扩展点**：新同学最常改哪里、有什么坑。

纯讲解，不设练习与自测；想动手改代码的学习者由 Agent 建议其显式调用 `guided-code-learning`。

## 红线

- 不执行会改状态的命令（安装依赖、迁移数据库、写文件）。
- 不把猜测的调用链写成事实；不确定就标注"未在代码中确认"。
- 不泄露仓库内的敏感信息（密钥、内网地址）到课程页面。

## 自检清单

- [ ] `entrypoints` 里每个符号都真实存在。
- [ ] 调用链能对应到具体文件与函数。
- [ ] 模块地图与仓库现状一致（无已删除/重命名的模块）。
- [ ] 讲解顺序是"问题 → 结构 → 路径 → 细节"，不是目录遍历。
- [ ] 论文 + 代码输入时，`relevance.mapping` 覆盖了主要方法模块。
